# UC-10 — Видати примірник

**Головний поглиблений Use Case лабораторної №2.** Основа:
[US-06](user-stories.md), [функціональні й нефункціональні вимоги](requirements.md),
[діаграма](diagrams/use-cases.puml), [правила №1](../spec.md).
Це специфікація поведінки майбутнього застосунку, а не реалізований процес.

## 1. Назва

UC-10 «Видати примірник». Незмінний ID; перевірка права й визначення черги
описані нижче як внутрішні кроки. UC-15 є включеною поведінкою обчислення
фізичної доступності, а не самостійною метою бібліотекаря.

## 2. Основний актор

Бібліотекар. Читач — одержувач примірника та учасник доменних даних;
наявність Reader не означає права самостійно оформлювати Loan.
Спільний актор «Користувач каталогу» успадковує лише пошук і перегляд,
не операцію видачі. Інтеграція сповіщень не запускає UC-10 і не дає права видачі.

## 3. Мета

Зафіксувати одну відкриту видачу фізичного Copy наявному Reader,
дотримуючись фізичного стану, активної черги, хронології та історії операцій.

## 4. Передумови

- Бібліотекар має чинну сесію і право оформляти видачу за NFR-07/NFR-08/NFR-10.
- Вибрані Reader і Copy існують; Copy посилається на наявний Book.
- Форма дозволяє подати loaned_at і due_at. Коректність дат і можливість
  видачі перевіряються потоком, а не припускаються наперед.

Порушення передумов обробляються до зміни доменних даних. Відсутність
фізичної доступності або пріоритету не виключає сценарій із розгляду:
це описані нижче альтернативи, які потрібно вміти відхилити.

## 5. Тригер

Бібліотекар підтверджує команду видачі вибраного примірника читачеві
з указаними датами. Отримане читачем сповіщення не замінює цю команду.

## 6. Основний сценарій

Основна гілка — активних бронювань Book немає.

1. Бібліотекар подає reader_id, copy_id, loaned_at і due_at.
2. Система перевіряє чинну сесію та роль, обов'язкові поля й наявність
   посилань. Перевіряє `due_at >= loaned_at`; рівність дозволена.
3. Через включену поведінку UC-15 визначає, що Copy.state = active
   і немає його Loan із порожнім returned_at.
4. Система визначає активну чергу Book: тільки Reservation.status = active,
   порядок за reserved_at, потім лексикографічно за канонічним UUID нижнього
   регістру. Для порожньої черги дозволяє видачу наявному Reader.
5. У єдиній атомарній операції система забезпечує актуальність перевірок
   доступності та права, створює Loan з новим UUID, поданими FK і датами,
   порожнім returned_at. Гарантує не більше одного відкритого Loan цього Copy
   навіть при конкурентних запитах. Спосіб реалізації атомарності не нав'язується.
6. Після фіксації даних система повертає підтвердження видачі з id Loan.
   У межах профілю NFR-03/NFR-05 p95 відповіді не перевищує 3 с;
   перевірки обігу не пропускаються заради досягнення цього часу.

## 7. Альтернативні сценарії

- **A1 — Перше активне бронювання належить цьому читачеві (крок 4).**
  Право надається першому читачеві черги. У кроці 5 разом зі створенням Loan
  саме перша Reservation стає fulfilled. Решта бронювань незмінні, наступне
  активне бронювання очолює чергу. Повторні бронювання зберігаються окремо.
- **A2 — Перше бронювання належить іншому читачеві.** Відмова через пріоритет
  черги, без нового Loan та зміни Reservation. Доступний фізично Copy
  не означає право конкретного читача отримати його.
- **A3 — Copy lost або written_off, чи має відкритий Loan (крок 3/5).**
  Відмова з відповідною причиною за REQ-17, без додаткової видачі.
  Пріоритет між кількома одночасними причинами відмови не задається новим правилом.
- **A4 — Конкурентна видача (крок 5).** Для двох коректних одночасних спроб
  одного доступного Copy без черги рівно одна створює Loan, інша
  відхиляється через уже відкриту видачу. Історія попередніх видач незмінна.
- **A5 — Некоректна хронологія (крок 2).** due_at раніше loaned_at
  спричиняє відмову без зміни даних; due_at, рівний loaned_at, проходить.
- **A6 — Звернення після сповіщення.** Потік починається заново з актуальних
  даних. Попередня доставка не резервує конкретний Copy і не обходить
  перевірку відкритої видачі або черги. SC-27 прямо покриває випадок,
  коли примірник уже має відкритий Loan; окремого прикладу зміни голови
  черги після повідомлення поки немає.

## 8. Винятки

- **X1 — Немає чинної сесії/права:** API повертає відповідно 401/403
  за NFR-07/NFR-08, не виконує видачу й не розкриває захищених даних.
  Це критерії майбутніх API-перевірок; SC-19–SC-27 їх зараз не виконують.
- **X2 — Неповні дані або відсутні посилання:** відмова з позначенням
  поля/зв'язку за REQ-11; це супутній контракт до основних вимог видачі.
- **X3 — Збій до фіксації:** атомарна операція не залишає частковий Loan
  або fulfilled без відповідної успішної видачі. Якщо дані вже зафіксовані,
  але відповідь втрачено, тайм-аут не доводить відкату. Гарантія «рівно один
  раз» для повторного HTTP-запиту не визначена; не можна приписувати її NFR.
- **X4 — Усі 50 робочих HTTP-слотів зайняті:** надлишковий запит
  отримує 503 за ≤1 с без доменних змін згідно з NFR-06. Це окрема межа
  запитів, а не безпосередня заборона 51-го активного користувача.
- **X5 — Помилка сповіщення:** належить UC-13/UC-17, а не змінює результат
  уже оформленої видачі. Інтеграція не є додатковою передумовою UC-10.

Повідомлення акторові українською, без SQL/stack trace/секретів (NFR-11).

## 9. Постумови

**Успіх:** є рівно один новий Loan з потрібними FK і датами, returned_at
порожній; для Copy не більше одного відкритого Loan. За видачі першому
бронюванню воно атомарно fulfilled. Інші бронювання, Copy.state та попередня
історія незмінні. Похідна доступність не записується окремим атрибутом.

**Відхилення до фіксації:** новий Loan не створено, доменні дані незмінні.
Для втрати відповіді після фіксації діє обмеження X3, а не неправдива
постумова «будь-яка помилка означає відсутність запису».

## 10. Трасування UC-10 → сценарії → функціональні вимоги → NFR

Нижче наведено фактичні REQ-теги сценаріїв. NFR у останньому стовпці —
умови приймання відповідного потоку, **не твердження про їх перевірку
цими Gherkin-кроками**. В основній матриці та діаграмі NFR немає.

| Сценарій | Функціональні вимоги з фактичних тегів | Пов'язаний потік | NFR як умови приймання |
|---|---|---|---|
| SC-19 | REQ-11, REQ-13, REQ-16, REQ-18 | Основний; рівний і пізніший due_at | NFR-05, NFR-07, NFR-08, NFR-09 |
| SC-20 | REQ-15, REQ-16, REQ-18 | A1: черга й атомарний fulfilled | NFR-05, NFR-08 |
| SC-21 | REQ-16, REQ-17 | A2/A3: недоступність або пріоритет | NFR-08, NFR-11 |
| SC-22 | REQ-17, REQ-19 | A4: конкурентна видача | NFR-03, NFR-05, NFR-06 |
| SC-23 | REQ-13 | A5: для UC-10 релевантний лише рядок due_at | NFR-11 |
| SC-27 | REQ-16, REQ-17, REQ-19, REQ-24 | A6: повторна перевірка після сповіщення | NFR-07, NFR-08, NFR-10 |

Усі шість сценаріїв мають тег US-06; SC-23 також US-07, але його приклад
returned_at належить UC-11. SC-19 додатково US-09/REQ-11; SC-27 також
US-08. SC-18 (US-05/REQ-15) підтримує правило сортування черги, однак
не видається за прямий сценарій US-06. REQ-24 не означає, що сама видача
не змінює Loan: незмінність стосується сповіщення, а видача змінює дані
тільки після повторної перевірки за її власними вимогами.

Наскрізні умови застосування NFR:

| NFR | Застосування до UC-10 та майбутня перевірка |
|---|---|
| NFR-01 | Форма бібліотекаря на viewport 1280 × 720 без горизонтального прокручування |
| NFR-02 | Успішна видача й відмова в усіх 8 погоджених комбінаціях браузер/версія/ОС |
| NFR-03 | 25/50 активних користувачів; ≤1% технічних помилок у кожному прогоні |
| NFR-04 | Стосується лише попереднього пошуку UC-07; ціль 2 с не підміняє час видачі |
| NFR-05 | Видача: p95 ≤3 с після фіксації за даними та профілем requirements.md |
| NFR-06 | 50 одночасних HTTP-запитів, надлишковим 503 ≤1 с, без часткового запису |
| NFR-07 | 100% запитів без чинної сесії відхилено, API 401 |
| NFR-08 | Лише бібліотекар оформлює Loan; читач/підміна ролі відхиляються, API 403 |
| NFR-09 | HTTPS/TLS ≥1.2, 0 визначених витоків персональних даних/секретів |
| NFR-10 | Межа бездіяльності 30 хв і вихід перевіряються до виконання операції |
| NFR-11 | Українські підписи й причини відмов, без внутрішніх технічних подробиць |
| NFR-12 | Браузерна робота без окремого клієнта/плагінів, сервер Linux x64 |

NFR-04 є лише допоміжним зв'язком із підготовкою, решта — безпосередні
умови середовища та приймання UC-10. Числа й профіль не перевизначаються
цим документом: джерело — незмінні погоджені NFR у requirements.md.
Поведінкові, навантажувальні та безпекові перевірки ще не виконані.

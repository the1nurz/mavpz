# EARS-вимоги — «Бібліотека»

Контракт: [spec.md](spec.md), AC-01–AC-05; правила даних:
[специфікація №1](../spec.md) і [ADR-0003](../adr/0003-derived-availability.md).
Це вимоги до майбутньої поведінки, а не твердження про реалізований застосунок.
WHEN задає подію, WHILE — стан; IF … THEN — небажану умову та реакцію.
Ubiquitous задає постійний інваріант. Кожне «повинна» стосується системи.
Відхилена операція не змінює доменні дані; успіх передбачає виконання всіх
застосовних інваріантів нижче. Правила авторизації тут не визначаються.

## Читачі та каталог

- **REQ-01 — WHEN:** WHEN бібліотекар подає нового читача з `full_name`,
  унікальним непорожнім `email` і `registered_at`, система повинна створити
  Reader з окремим UUID та повернути його `id` (AC-01, AC-02).
- **REQ-02 — IF:** IF під час збереження Reader його email вже належить іншому
  Reader, THEN система повинна відхилити операцію з причиною «email зайнятий»
  (AC-02). Порівняння не вводить нових правил нормалізації email.
- **REQ-03 — WHEN:** WHEN бібліотекар додає автора з `full_name`, `birth_year`
  або видавця з `name`, `country`, система повинна створити відповідний Author
  або Publisher з окремим UUID, дозволяючи відсутність пов'язаних книг (AC-01, AC-02).
- **REQ-04 — WHEN:** WHEN бібліотекар додає видання з `title`, унікальним ISBN,
  `publication_year`, одним наявним Publisher і щонайменше одним наявним Author,
  система повинна створити Book з окремим UUID та цими зв'язками, дозволяючи
  кількох авторів і відсутність примірників (AC-01, AC-02).
- **REQ-05 — IF:** IF під час збереження Book ISBN належить іншому Book,
  THEN система повинна відхилити операцію з причиною «ISBN зайнятий» (AC-02).
- **REQ-06 — WHEN:** WHEN бібліотекар додає примірник наявної Book з унікальним
  `inventory_number` та допустимим `state`, система повинна створити Copy
  з окремим UUID і посиланням на цю Book (AC-01, AC-02).
- **REQ-07 — IF:** IF під час збереження Copy інвентарний номер належить іншому
  Copy, THEN система повинна відхилити операцію з причиною «інвентарний номер
  зайнятий» (AC-02).
- **REQ-08 — WHEN:** WHEN читач шукає книгу за точним ISBN, система повинна
  повернути відповідну Book або порожній результат, якщо ISBN не знайдено
  (AC-01). Це мінімальний перевірюваний спосіб пошуку за наявним ключем.
- **REQ-09 — WHEN:** WHEN читач переглядає фізичну доступність книги, система
  повинна показати для кожного її Copy результат умови `state = active`
  і відсутності Loan з порожнім `returned_at`; для книги без Copy показати
  відсутність примірників (AC-01, AC-03).

## Постійні обмеження даних

- **REQ-10 — Ubiquitous:** Система повинна зберігати незмінну структуру моделі
  №1: сім сутностей, 30 атрибутів, сім зв'язків, UUID PK/FK, прямий Author–Book
  M:N без власних атрибутів і обчислювану, а не збережену доступність (AC-02).
- **REQ-11 — IF:** IF операція залишає порожнім обов'язковий атрибут із
  специфікації №1, посилається на відсутню сутність або порушує визначені там
  кардинальності, THEN система повинна відхилити операцію і вказати порушений
  атрибут або зв'язок (AC-02). Порожній `Loan.returned_at` дозволений.
- **REQ-12 — IF:** IF записуваний `Copy.state` не належить множині
  {`active`, `lost`, `written_off`} або `Reservation.status` не належить
  {`active`, `fulfilled`, `cancelled`, `expired`}, THEN система повинна
  відхилити операцію і вказати недопустиме значення (AC-02).
- **REQ-13 — IF:** IF у записуваному Loan `due_at < loaned_at` або непорожній
  `returned_at < loaned_at`, THEN система повинна відхилити операцію
  з причиною порушення хронології (AC-02).

## Бронювання та право на видачу

- **REQ-14 — WHEN:** WHEN наявний читач бронює наявну Book, система повинна
  створити окрему Reservation з новим UUID, `reader_id`, `book_id`,
  `reserved_at` та `status = active` незалежно від кількості фізично доступних
  Copy, у тому числі за відсутності Copy та при повторному бронюванні (AC-01, AC-02).
- **REQ-15 — WHILE:** WHILE книга має активні Reservation, система повинна
  визначати перше бронювання за зростанням `reserved_at`, потім `id`,
  порівнюючи UUID лексикографічно в канонічному записі нижнього регістру;
  неактивні бронювання не повинні входити до цієї черги (AC-02, AC-03).
- **REQ-16 — WHEN:** WHEN бібліотекар перевіряє право на видачу фізично
  доступного Copy наявному читачеві, система повинна дозволити видачу лише
  читачеві першої активної Reservation його Book або будь-якому наявному
  читачеві за відсутності активних Reservation цієї Book (AC-03).
- **REQ-17 — IF:** IF запитана видача стосується Copy зі станом `lost` чи
  `written_off`, Copy з відкритим Loan або читача без права за REQ-16,
  THEN система повинна відхилити видачу, вказавши відповідно фізичний стан,
  відкриту видачу або пріоритет черги (AC-03).

## Видача та повернення

- **REQ-18 — WHEN:** WHEN бібліотекар оформлює дозволену REQ-16 видачу
  фізично доступного Copy з коректними датами, система повинна створити Loan
  з новим UUID, `reader_id`, `copy_id`, `loaned_at`, `due_at` і порожнім
  `returned_at`; якщо право визначила перша Reservation, одночасно перевести
  саме її в `fulfilled`, зберігши решту бронювань (AC-01–AC-03).
- **REQ-19 — WHILE:** WHILE Copy має відкритий Loan, система повинна
  забезпечувати не більше одного відкритого Loan цього Copy, зокрема
  при одночасних спробах видачі (AC-03).
- **REQ-20 — WHEN:** WHEN бібліотекар реєструє повернення відкритого Loan
  з датою не раніше `loaned_at`, система повинна записати цю дату в
  `returned_at`, зберегти решту історії та повторно обчислити фізичну
  доступність Copy за REQ-09 без автоматичної зміни його `state` (AC-01–AC-03).
- **REQ-21 — WHEN:** WHEN бібліотекар записує допустимий фізичний стан Copy,
  система повинна зберегти `state` та обчислювати доступність за REQ-09,
  не змінюючи історію Loan і не закриваючи відкриту видачу (AC-01, AC-02).

## Зовнішній сервіс сповіщень — погоджене припущення A1

- **REQ-22 — WHEN:** WHEN система визначає можливість запропонувати фізично
  доступний Copy першому читачеві активної черги його Book, система повинна
  передати зовнішньому сервісу `Reader.email` цього читача та ідентифікатор
  і назву Book для повідомлення про можливість отримання (AC-04).
- **REQ-23 — IF:** IF зовнішній сервіс повертає помилку передавання
  сповіщення, THEN система повинна показати бібліотекарю помилку з посиланням
  на відповідну Book (AC-04).
- **REQ-24 — Ubiquitous:** Система повинна зберігати Loan, Reservation,
  Copy та порядок черги незміненими внаслідок самого передавання сповіщення
  або помилки сервісу; перед фактичною видачею право перевіряється заново
  за REQ-16–REQ-19 (AC-03, AC-04).

## Межі перевірки

Кожний ID є окремою ціллю для майбутніх сценаріїв і трасування (AC-05).
REQ-10 перевіряється структурним аудитом і переглядом моделі; часові правила,
черга, конкурентна видача та сповіщення потребують поведінкових сценаріїв
і майбутньої реалізації. Статуси `cancelled` і `expired` успадковані з №1;
політика скасування/закінчення строку, ліміти видач, штрафи та гарантії доставки
не визначені й не вводяться цим документом. Сповіщення не гарантує доступність
на момент звернення читача. Журнал доставки й повторні спроби поза A1.

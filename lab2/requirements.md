# EARS-вимоги — «Бібліотека»

Контракт: [spec.md](spec.md), AC-01–AC-05; правила даних:
[специфікація №1](../spec.md) і [ADR-0003](../adr/0003-derived-availability.md).
Це вимоги до майбутньої поведінки, а не твердження про реалізований застосунок.
WHEN задає подію, WHILE — стан; IF … THEN — небажану умову та реакцію.
Ubiquitous задає постійний інваріант. Кожне «повинна» стосується системи.
Відхилена операція не змінює доменні дані; успіх передбачає виконання всіх
застосовних інваріантів нижче. Автентифікацію та новий погоджений контракт
авторизації визначено окремо в NFR-07, NFR-08 і NFR-10.

## Читачі та каталог

- **REQ-01 — WHEN:** WHEN бібліотекар подає нового читача з `full_name`,
  унікальним непорожнім `email` і `registered_at`, система повинна створити
  Reader з окремим UUID та повернути його `id` (AC-01, AC-02).
- **REQ-02 — IF:** IF під час збереження Reader його email вже належить іншому
  Reader, THEN система повинна відхилити операцію з причиною «email зайнятий»
  (AC-02). Порівняння не вводить нових правил нормалізації email.
- **REQ-03 — WHEN:** WHEN бібліотекар додає автора з `full_name`, `birth_year`
  або видавця з `name`, `country`, система повинна створити відповідний Author
  або Publisher з окремим UUID, дозволяючи відсутність пов'язаних книг (AC-01, AC-02).
- **REQ-04 — WHEN:** WHEN бібліотекар додає видання з `title`, унікальним ISBN,
  `publication_year`, одним наявним Publisher і щонайменше одним наявним Author,
  система повинна створити Book з окремим UUID та цими зв'язками, дозволяючи
  кількох авторів і відсутність примірників (AC-01, AC-02).
- **REQ-05 — IF:** IF під час збереження Book ISBN належить іншому Book,
  THEN система повинна відхилити операцію з причиною «ISBN зайнятий» (AC-02).
- **REQ-06 — WHEN:** WHEN бібліотекар додає примірник наявної Book з унікальним
  `inventory_number` та допустимим `state`, система повинна створити Copy
  з окремим UUID і посиланням на цю Book (AC-01, AC-02).
- **REQ-07 — IF:** IF під час збереження Copy інвентарний номер належить іншому
  Copy, THEN система повинна відхилити операцію з причиною «інвентарний номер
  зайнятий» (AC-02).
- **REQ-08 — WHEN:** WHEN читач шукає книгу за точним ISBN, система повинна
  повернути відповідну Book або порожній результат, якщо ISBN не знайдено
  (AC-01). Це мінімальний перевірюваний спосіб пошуку за наявним ключем.
- **REQ-09 — WHEN:** WHEN читач переглядає фізичну доступність книги, система
  повинна показати для кожного її Copy результат умови `state = active`
  і відсутності Loan з порожнім `returned_at`; для книги без Copy показати
  відсутність примірників (AC-01, AC-03).

## Постійні обмеження даних

- **REQ-10 — Ubiquitous:** Система повинна зберігати незмінну структуру моделі
  №1: сім сутностей, 30 атрибутів, сім зв'язків, UUID PK/FK, прямий Author–Book
  M:N без власних атрибутів і обчислювану, а не збережену доступність (AC-02).
- **REQ-11 — IF:** IF операція залишає порожнім обов'язковий атрибут із
  специфікації №1, посилається на відсутню сутність або порушує визначені там
  кардинальності, THEN система повинна відхилити операцію і вказати порушений
  атрибут або зв'язок (AC-02). Порожній `Loan.returned_at` дозволений.
- **REQ-12 — IF:** IF записуваний `Copy.state` не належить множині
  {`active`, `lost`, `written_off`} або `Reservation.status` не належить
  {`active`, `fulfilled`, `cancelled`, `expired`}, THEN система повинна
  відхилити операцію і вказати недопустиме значення (AC-02).
- **REQ-13 — IF:** IF у записуваному Loan `due_at < loaned_at` або непорожній
  `returned_at < loaned_at`, THEN система повинна відхилити операцію
  з причиною порушення хронології (AC-02).

## Бронювання та право на видачу

- **REQ-14 — WHEN:** WHEN наявний читач бронює наявну Book, система повинна
  створити окрему Reservation з новим UUID, `reader_id`, `book_id`,
  `reserved_at` та `status = active` незалежно від кількості фізично доступних
  Copy, у тому числі за відсутності Copy та при повторному бронюванні (AC-01, AC-02).
- **REQ-15 — WHILE:** WHILE книга має активні Reservation, система повинна
  визначати перше бронювання за зростанням `reserved_at`, потім `id`,
  порівнюючи UUID лексикографічно в канонічному записі нижнього регістру;
  неактивні бронювання не повинні входити до цієї черги (AC-02, AC-03).
- **REQ-16 — WHEN:** WHEN бібліотекар перевіряє право на видачу фізично
  доступного Copy наявному читачеві, система повинна дозволити видачу лише
  читачеві першої активної Reservation його Book або будь-якому наявному
  читачеві за відсутності активних Reservation цієї Book (AC-03).
- **REQ-17 — IF:** IF запитана видача стосується Copy зі станом `lost` чи
  `written_off`, Copy з відкритим Loan або читача без права за REQ-16,
  THEN система повинна відхилити видачу, вказавши відповідно фізичний стан,
  відкриту видачу або пріоритет черги (AC-03).

## Видача та повернення

- **REQ-18 — WHEN:** WHEN бібліотекар оформлює дозволену REQ-16 видачу
  фізично доступного Copy з коректними датами, система повинна створити Loan
  з новим UUID, `reader_id`, `copy_id`, `loaned_at`, `due_at` і порожнім
  `returned_at`; якщо право визначила перша Reservation, одночасно перевести
  саме її в `fulfilled`, зберігши решту бронювань (AC-01–AC-03).
- **REQ-19 — WHILE:** WHILE Copy має відкритий Loan, система повинна
  забезпечувати не більше одного відкритого Loan цього Copy, зокрема
  при одночасних спробах видачі (AC-03).
- **REQ-20 — WHEN:** WHEN бібліотекар реєструє повернення відкритого Loan
  з датою не раніше `loaned_at`, система повинна записати цю дату в
  `returned_at`, зберегти решту історії та повторно обчислити фізичну
  доступність Copy за REQ-09 без автоматичної зміни його `state` (AC-01–AC-03).
- **REQ-21 — WHEN:** WHEN бібліотекар записує допустимий фізичний стан Copy,
  система повинна зберегти `state` та обчислювати доступність за REQ-09,
  не змінюючи історію Loan і не закриваючи відкриту видачу (AC-01, AC-02).

## Зовнішній сервіс сповіщень — погоджене припущення A1

- **REQ-22 — WHEN:** WHEN система визначає можливість запропонувати фізично
  доступний Copy першому читачеві активної черги його Book, система повинна
  передати зовнішньому сервісу `Reader.email` цього читача та ідентифікатор
  і назву Book для повідомлення про можливість отримання (AC-04).
- **REQ-23 — IF:** IF зовнішній сервіс повертає помилку передавання
  сповіщення, THEN система повинна показати бібліотекарю помилку з посиланням
  на відповідну Book (AC-04).
- **REQ-24 — Ubiquitous:** Система повинна зберігати Loan, Reservation,
  Copy та порядок черги незміненими внаслідок самого передавання сповіщення
  або помилки сервісу; перед фактичною видачею право перевіряється заново
  за REQ-16–REQ-19 (AC-03, AC-04).

## Нефункціональні вимоги (NFR)

NFR-01–NFR-12 погоджені користувачем 23.10.2026 як проєктні вимоги до
майбутньої реалізації. Це цільові значення, а не досягнуті результати.
Вони не змінюють REQ-01–REQ-24, ER-модель або погоджені правила обігу.

### Спільний профіль вимірювання продуктивності

- Тестові дані: 10 000 Book, 30 000 Copy, 5 000 Reader, 100 000 Loan,
  20 000 Reservation; пов'язані Author/Publisher забезпечують цілісність.
  Дані синтетичні, з погодженими ключами, станами та чергою.
- Застосунок і БД сумарно обмежені 2 vCPU, 4 GiB RAM, диском SSD.
  Генератор навантаження працює окремо; RTT до сервера не перевищує 20 мс.
  Версії компонентів, конфігурацію та набір даних фіксують у протоколі.
- Один активний користувач навантажувального тесту — один віртуальний
  користувач, який циклічно виконує операції. Він має не більше одного
  незавершеного запиту та паузу 5 с після відповіді перед наступною операцією.
  Це не кількість зареєстрованих читачів, сесій чи відкритих вкладок.
- Для 25 та 50 активних користувачів окремо: 5 хв прогрівання,
  15 хв вимірювання, 3 незалежні прогони з відновленням початкових даних.
  Суміш операцій: 70% пошуку за ISBN, 15% видачі, 15% бронювання;
  облікові записи мають відповідні права. Ресурси для видачі та бронювання
  готуються так, щоб коректні запити не спричиняли очікуваних бізнес-відмов.
- Час відповіді: від надсилання HTTP-запиту генератором до отримання
  останнього байта відповіді. p95 — значення впорядкованої вибірки
  з номером ceil(0.95 × N), окремо для кожної операції та прогону,
  без прогрівання. У протоколі зазначають N, помилки й тайм-аути;
  їх не приховують вилученням зі статистики. Тайм-аут вважається
  перевищенням цільового часу та технічною помилкою.
- Успіх записувальної операції повертається після фіксації даних.
  Фактична доставка зовнішнього сповіщення не входить до цих часових меж.
  Критерії мають виконуватися в кожному з трьох прогонів.

### NFR-01 — Ролі та пристрої

**Вимога:** для читача й бібліотекаря підтримується робота з ПК або ноутбука
за мінімального viewport 1280 × 720 CSS px.
**Умови:** браузери NFR-02, масштаб 100%; основні форми пошуку, доступності,
бронювання, реєстрації, каталогу, примірників, видачі та повернення.
**Критерій прийняття:** у 100% цих форм усі поля, повідомлення та кнопки
доступні без горизонтального прокручування; вертикальне дозволене.
**Перевірка:** огляд і браузерні тести кожної форми під обома застосовними ролями.

### NFR-02 — Браузери та клієнтські платформи

**Вимога:** підтримуються Chrome та Firefox, дві останні стабільні основні
версії кожного на дату початку приймання, на Windows 11 та Linux x64.
**Умови:** точні версії браузерів і Linux-дистрибутив фіксують до тестування;
разом 8 комбінацій браузер/версія/ОС, viewport не менше NFR-01.
**Критерій прийняття:** 100% основних операцій NFR-01 проходять у кожній
комбінації без помилок, специфічних для браузера або ОС.
**Перевірка:** однакова матриця функціональних перевірок сумісності
з протоколом версій та результатів для всіх 8 комбінацій.

### NFR-03 — Розрахункове навантаження

**Вимога:** нормальне навантаження — 25 одночасних активних користувачів;
максимальне розрахункове — 50 за спільним профілем вище.
**Умови:** по 3 прогони для кожного рівня, без фонового стороннього навантаження.
**Критерій прийняття:** частка неочікуваних технічних помилок не перевищує
1% усіх запитів у кожному прогоні; HTTP 5xx, транспортні помилки й тайм-аути
рахуються як технічні помилки. У межах 50 користувачів HTTP 503 не є винятком.
**Перевірка:** навантажувальний тест із підрахунком усіх результатів;
очікувані бізнес-відмови тестуються окремо, а не маскують технічні збої.

### NFR-04 — Час пошуку

**Вимога:** p95 часу відповіді пошуку за точним ISBN не перевищує 2 с.
**Умови:** обидва рівні навантаження NFR-03, дані та вимірювання за спільним
профілем; пошуковий набір включає наявні та відсутні ISBN і фіксується в протоколі.
**Критерій прийняття:** p95 ≤2 с для пошуку в кожному прогоні при 25 і 50
користувачах; правильність результатів не поступається REQ-08.
**Перевірка:** гістограма часу запитів пошуку та звіряння результатів із набором даних.

### NFR-05 — Час видачі та бронювання

**Вимога:** p95 часу відповіді не перевищує 3 с окремо для видачі та бронювання.
**Умови:** обидва рівні NFR-03, спільний профіль, коректні дані та права;
успіх означає зафіксований Loan або Reservation, а не лише прийняття запиту.
**Критерій прийняття:** p95 ≤3 с для кожної з двох операцій у кожному прогоні;
збережені результати відповідають REQ-14, REQ-16–REQ-19.
**Перевірка:** окремі гістограми та перевірка записів, станів черги
і відсутності подвійних відкритих видач після прогону.

### NFR-06 — Межа HTTP-запитів та перевантаження

**Вимога:** 50 активних користувачів — максимальне розрахункове навантаження
за NFR-03; окремо сервер допускає одночасну обробку максимум 50 HTTP-запитів
операцій бібліотеки. Ліміт запитів спільний для всіх екземплярів застосунку.
Запит займає слот від допуску до обробки до завершення відповіді;
51-й та наступні запити, які застали всі слоти зайнятими, отримують HTTP 503
не пізніше ніж за 1 с, без доменних змін. Запити відхилення не займають
робочі слоти. Ліміт не є обмеженням кількості зареєстрованих користувачів
або сесій. Саме перевищення 50 активних користувачів не вимагає HTTP 503,
якщо одночасно обробляється менше 50 запитів; гарантії NFR-03–NFR-05
поза розрахунковим навантаженням не надаються.
**Умови:** прогін при 75 активних користувачах, 5 хв прогрівання та 15 хв
спостереження; додатково синхронізований пакет 75 запитів із контрольованим
утриманням перших 50 у робочих слотах, щоб перевищення було гарантованим.
**Критерій прийняття:** максимум 50 зайнятих слотів; 100% надлишкових запитів
контрольного пакета отримують 503 за ≤1 с; 0 часткових доменних записів
від відхилених запитів. Після звільнення слотів коректні запити приймаються знову.
**Перевірка:** тест перевантаження з метрикою одночасної обробки,
кодами/часом відповідей та звірянням даних до й після відмов.

### NFR-07 — Автентифікація

**Вимога:** усі операції з правами NFR-08 потребують чинної автентифікованої
сесії; ідентичність визначається сервером, а не полем ролі з клієнта.
**Умови:** для кожної захищеної операції виконують запити без сесії,
з некоректною, простроченою та анульованою сесією, включно з прямим API-доступом.
**Критерій прийняття:** 100% таких запитів відхиляються (HTTP 401 для API),
без повернення захищених даних або зміни доменних записів.
**Перевірка:** негативні API-тести та порівняння даних до й після кожної спроби.

### NFR-08 — Новий погоджений контракт авторизації

**Вимога:** погоджено 23.10.2026 як новий нефункціональний контракт доступу,
без зміни REQ-01–REQ-24 або ER. Читач може шукати, переглядати доступність
і бронювати лише від власного імені. Бібліотекар веде каталог і примірники,
реєструє читачів, оформлює видачу та повернення. Для решти поєднань ролі
й захищеної операції доступ за замовчуванням заборонений. Повідомлення
надсилається системною взаємодією A1, а не прямою командою читача;
зовнішній сервіс не отримує інтерактивних прав бібліотекаря.
**Умови:** матриця роль/операція для всіх основних операцій NFR-01;
окремі спроби підміни reader_id і клієнтського поля ролі.
**Критерій прийняття:** 100% дозволених комбінацій доступні за коректних
передумов; 100% заборонених дій і спроб бронювати за іншого читача відхиляються
на сервері (HTTP 403 для API), без зміни даних і розкриття захищених полів.
**Перевірка:** позитивні й негативні API-тести матриці прав, а не лише приховування
кнопок. Спосіб зберігання облікових записів/ролей цим контрактом не визначається;
нові ER-сутності не додаються.

### NFR-09 — Захист персональних даних

**Вимога:** клієнтське передавання захищених даних і взаємодія з сервісом A1
відбуваються лише через HTTPS із TLS не нижче 1.2. Відповіді читачеві
не містять чужих email; журнали не містять паролів, токенів сесій або повних email.
**Умови:** відомі контрольні email, паролі й токени вводять у позитивних
та негативних тестах; перевіряють усі згенеровані журнали й відповіді читачеві.
**Критерій прийняття:** 0 передавань захищених даних відкритим HTTP,
0 успішних TLS-з'єднань нижче 1.2; 0 чужих email у відповідях читачеві;
0 зазначених секретів/повних email у журналах. Перенаправлення HTTP
не повинне передавати захищені дані перед встановленням HTTPS.
**Перевірка:** TLS-проби, аналіз мережевих запитів, автоматичний пошук
контрольних значень у журналах і перевірка полів відповідей.

### NFR-10 — Життєвий цикл сесії

**Вимога:** сесія завершується після 30 хв бездіяльності; успішний вихід
анулює її на сервері. Cookie сесії має Secure, HttpOnly та SameSite=Lax
або Strict. Активністю вважається прийнятий автентифікований запит користувача;
фонове опитування не подовжує сесію.
**Умови:** тест із контрольованим часом і відсутністю активності;
перевірка безпосередньо до та на межі 30 хв, а також після виходу.
**Критерій прийняття:** до межі сесія чинна; на межі й після неї
захищені запити відхиляються за NFR-07; 100% повторних спроб після виходу
також відхиляються; усі cookie сесії мають зазначені атрибути.
**Перевірка:** API-тести з контрольованим часом, повторне використання
старої cookie та огляд Set-Cookie у браузері/HTTP-клієнті.

### NFR-11 — Українська локалізація

**Вимога:** основна мова інтерфейсу — українська; повідомлення про помилки
вказують причину та, для помилок введення, відповідне поле.
**Умови:** усі основні форми NFR-01 і класи помилок ключів, обов'язковості,
посилань, станів, дат, черги, видачі, сервісу, сесії, прав та перевантаження.
**Критерій прийняття:** 100% системних підписів, кнопок і повідомлень
у перевіреному переліку українською; 0 stack trace, SQL або секретів
у користувацьких повідомленнях. Дані, введені користувачем, не перекладаються;
технічні ID і стандартні коди протоколу можуть залишатися незмінними.
**Перевірка:** звіряння словника інтерфейсу з усіма відображеними елементами,
відтворення кожного класу помилок та огляд тексту відповіді/інтерфейсу.

### NFR-12 — Тип застосунку та технологічні межі

**Вимога:** вебзастосунок працює через браузери NFR-02 без обов'язкового
встановлення окремого клієнта або плагінів; серверна платформа — Linux x64.
Конкретні фреймворк і СУБД не нав'язуються цією вимогою.
**Умови:** чиста серверна система Linux x64 і чисті профілі підтримуваних
браузерів; версії ОС і необхідні серверні залежності зазначені в інструкції
розгортання майбутнього застосунку.
**Критерій прийняття:** застосунок розгортається за інструкцією;
100% основних операцій NFR-01 доступні без клієнтських інсталяцій/плагінів
у всіх комбінаціях NFR-02. Обмеження ресурсів вимірювання задає спільний профіль.
**Перевірка:** контрольне розгортання на чистому стенді й матриця сумісності;
встановлення службових засобів тестування не є вимогою до кінцевого користувача.

## Межі перевірки

Кожний ID є окремою ціллю для майбутніх сценаріїв і трасування (AC-05).
REQ-10 перевіряється структурним аудитом і переглядом моделі; часові правила,
черга, конкурентна видача та сповіщення потребують поведінкових сценаріїв
і майбутньої реалізації. Статуси `cancelled` і `expired` успадковані з №1;
політика скасування/закінчення строку, ліміти видач, штрафи та гарантії доставки
не визначені й не вводяться цим документом. Сповіщення не гарантує доступність
на момент звернення читача. Журнал доставки й повторні спроби поза A1.

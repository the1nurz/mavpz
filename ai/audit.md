Нижче зафіксовано рішення студента після перегляду. AI-помічник оформив записи та зіставив фрагменти. Повний дослівний фідбек збережено в [prompts.md](prompts.md). Це не три початкові помилки AI.

## A1 — мінімум один примірник (K2)

**Початковий фрагмент специфікації:**

> K2. Примірники: книга може щонайменше один фізичний примірник.

**Початковий фрагмент моделі:**

```mermaid
Book ||--|{ Copy : includes
```

**Рішення студента — дослівно:**

> A1. Кожна книга повинна мати хоча б один фізичний примірник. У K2 специфікації є неточне формулювання. У першій моделі кардинальність Book–Copy правильна, її змінювати не потрібно.

**Необхідна зміна:** уточнити K2 у специфікації: кожна книга має щонайменше один фізичний примірник. Кардинальність Book–Copy залишити без змін.

**Класифікація:** уточнення неоднозначної вимоги. Помилка моделі не підтверджена.

**Статус:** рішення отримано; зміну специфікації ще не внесено.

## A2 — порядок черги (K5)

**Початковий фрагмент специфікації:**

> K5. Черга: бронювання однієї книги обслуговуються в порядку їх створення, сортування за ID.

**Початкові фрагменти моделі:**

```text
Reservation {
    int id PK
    int reader_id FK
    int book_id FK
    datetime created_at
    string status
}
%% Reservation.id is assigned in increasing creation order.
%% Pending reservations for a Book are served by ascending Reservation.id.
```

**Рішення студента — дослівно:**

> A2. Чергу бронювань потрібно визначати за created_at, а якщо час однаковий — за Reservation.id. Перша модель описує обслуговування за ID та припускає, що ID призначаються послідовно. Я не хочу залежати від цього припущення.

**Необхідна зміна:** змінити K5 на впорядкування за зростанням `created_at`, за однакового часу — за `Reservation.id`. У коментарях моделі прибрати залежність порядку черги від послідовного призначення ID та описати новий порядок. Наявних атрибутів достатньо; змін структури не потрібно.

**Класифікація:** зміна вимоги після перегляду та усунення небажаного припущення. Перша модель узгоджувалася з початковим K5 за явно задокументованого припущення; це не доведена початкова помилка AI. Є реальна відмінність між новим рішенням і чинними коментарями моделі, яку потрібно усунути після дозволу на редагування.

**Статус:** рішення отримано; специфікацію та коментарі моделі ще не змінено.

## A3 — історія та активна видача (K4)

**Початковий фрагмент специфікації:**

> K4. Одночасна видача: один примірник не може одночасно перебувати у видачі в кількох читачів.

**Початкові фрагменти моделі:**

```text
Copy ||--o{ Loan : records
datetime returned_at
%% Loan.returned_at is NULL while the loan is open.
%% At most one open Loan per Copy; historical loans remain stored.
```

**Рішення студента — дослівно:**

> A3. Один фізичний примірник може мати багато історичних видач, але лише одну активну видачу одночасно. Кардинальність Copy–Loan 0..\* правильна. Потрібно окремо описати обмеження для активних видач.

**Необхідна зміна:** уточнити K4: історія примірника може містити багато Loan, але для одного `copy_id` допускається максимум один Loan із `returned_at = NULL`. Кардинальність Copy–Loan залишити `0..*`; коментар першої моделі вже описує це обмеження. Для майбутньої перевірки: друга відкрита видача того самого примірника заборонена, нова видача після закриття попередньої дозволена.

**Класифікація:** уточнення та посилення перевірюваності вимоги. Початкова модель уже містить правило однієї відкритої видачі; помилка кардинальності не підтверджена. Коментар Mermaid сам по собі не забезпечує обмеження на реальних даних.

**Статус:** рішення отримано; специфікацію не змінено, перевірки на даних не виконано.

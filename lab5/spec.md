## 3. Предметна область та межа системи

Бібліотека веде каталог видань Book, авторів Author, видавців Publisher, фізичних примірників Copy, читачів Reader, видач Loan і бронювань Reservation. Book — конкретне видання з ISBN; Copy — окремий фізичний примірник.

Читач шукає за ISBN, переглядає доступність і бронює лише від свого імені. Бібліотекар реєструє читачів, веде каталог і примірники, оформлює видачу та повернення; також має пошук і перегляд за ADR-L2-0003. «Користувач каталогу» — узагальнення цих ролей, а не третя роль доступу. Reader у БД не є компонентом автентифікації.

**У межі інформаційної системи:** браузерний UI, один серверний Backend з внутрішніми модулями, Data Access і спільна БД. UI виконується у браузері користувача; серверна платформа — Linux x64 за NFR-12. БД позначається як внутрішнє сховище, без вибору продукту чи сервера розгортання.

**За межею:** люди та зовнішній сервіс сповіщень A1. Браузер — середовище UI, а не додаткова бізнес-система. БД не є сторонньою бізнес-інтеграцією. Payment, OAuth та інші непідтверджені інтеграції не вводяться. Штрафи, оплата, продовження видачі, автоматичне завершення бронювань і нові права не додаються.

## 4. Модульна архітектура одного вебзастосунку

Обирається один модульний вебзастосунок: UI звертається до API/Backend; серверні компоненти викликають один одного всередині одного застосунку та працюють зі спільною БД через Data Access. Внутрішні виклики не означають окремих HTTP-сервісів. Мікросервіси, брокер, окремий сервер черги й кеш не потрібні для описаних вимог.

| ID | Компонент | Відповідальність |
|---|---|---|
| C1 | Вебінтерфейс (UI) | Форми читача й бібліотекаря, виклики API, показ результатів і українських причин відмов; UI не приймає остаточних бізнес-рішень |
| C2 | API/Backend | Приймання HTTP-запитів, допуск за NFR-06, перевірка сесії/прав, визначення поточного читача, передавання перевіреного контексту бізнес-компонентам, формування відповідей |
| C3 | Облік читачів | Реєстрація Reader, перевірка даних і унікальності email |
| C4 | Каталог і примірники | Author, Publisher, Book, створення Copy, фізичний стан, пошук за ISBN і показ обчисленої доступності |
| C5 | Обіг і бронювання | Створення Reservation, активна черга, обчислення доступності, право видачі, атомарна видача і повернення |
| C6 | Сповіщення | Визначення адресата за поточною доступністю/чергою у контексті A1, отримання email і даних Book, передавання A1 та обробка помилки |
| C7 | Доступ до даних (Data Access) | Читання й збереження доменних даних, виконання єдиної атомарної операції видачі без часткових змін |
| C8 | База даних | Спільне стале зберігання семи доменних сутностей та їхніх зв'язків |

Зовнішній компонент **A1 — Сервіс сповіщень** показується окремо від C1–C8. C2–C7 входять до одного серверного застосунку; C2 — його вхідний компонент. Контроль доступу й допуск HTTP-запитів — внутрішні обов'язки C2, а не додаткові сервери. Availability і Queue з Sequence відповідають внутрішнім функціям C5, які повторно використовуються через його інтерфейси. Кожна lifeline не потребує окремого компонента.

## 5. Provided/required інтерфейси та залежності

Provided — інтерфейс, який компонент надає; required — інтерфейс, якого він потребує. Наведені назви є контрактами логічної моделі, а не готовими URL, класами чи SDK. Внутрішні інтерфейси бізнес-компонентів не публікуються безпосередньо в інтернет.

| Інтерфейс | Надає (provided) | Потребує (required) | Операції та результат |
|---|---|---|---|
| IBackend | C2 | C1 | Операції форм для дозволених ролей; результат або причина відмови; для видачі успіх містить Loan.id після commit |
| IReaders | C3 | C2 | registerReader(full_name, email, registered_at) → Reader.id або помилка |
| ICatalogue | C4 | C2 | Додати автора/видавця/видання/примірник, знайти ISBN, переглянути доступність, записати Copy.state → дані або помилка |
| ICirculation | C5 | C2 | reserveBook, issueCopy, returnLoan → результат після фіксації або обґрунтована відмова |
| IAvailability | C5 | C4, C6 | computeAvailability(copy_id) → boolean зі стану Copy та відкритих Loan; жодного запису available |
| IQueue | C5 | C6 | getFirstActiveReservation(book_id) → перша active Reservation або відсутність; C5 також використовує це правило всередині видачі |
| INotifications | C6 | C2 у системному контексті A1 | Обробити вже визначену можливість сповіщення → результат передавання або помилка з Book.id; це не команда читача |
| IStore | C7 | C3, C4, C5, C6 | Читати посилання/ключі/стан/чергу, зберігати дозволені записи; issueCopyAtomically(reader_id, copy_id, loaned_at, due_at) → зафіксований Loan.id або відмова |
| IDatabase | C8 | C7 | Збереження, читання і транзакція; абстрактний контракт БД без вибору СУБД |
| INotificationGateway | A1 | C6 | transferNotification(email, book_id, title) → відомий результат передавання або помилка; отримання листа читачем не гарантується |

Для IStore права запису обмежуються відповідальністю викликача: C3 — Reader; C4 — каталог і Copy; C5 — Loan/Reservation; C6 — лише читання. C5 виконує власні обчислення доступності/черги без залежності на самого себе на Component Diagram.

Напрямок залежності йде від споживача до постачальника інтерфейсу. Дозволені міжкомпонентні залежності: C1 → C2; C2 → C3/C4/C5/C6; C3 → C7; C4 → C5/C7; C5 → C7; C6 → C5/C7/A1; C7 → C8. Прямих UI → БД, UI → бізнес-компонент, бізнес-компонент → БД в обхід C7 і циклів між компонентами немає. Шлях C6 → C2 для показу помилки не додається: C6 повертає результат виклику через INotifications, а C2 забезпечує його показ бібліотекарю через UI. Транспорт і час системного показу джерелами не визначені.

## 6. Доменні правила та транзакційна межа

1. Зберігаються 7 сутностей, 30 атрибутів, 7 зв'язків базової ER; PK/FK — UUID. ISBN, email та inventory_number — обов'язкові унікальні ключі. Книга має одного видавця, щонайменше одного автора та 0..* Copy. Фізична реалізація M:N не змінює концептуальну ER і тут не проєктується.
2. Copy.state належить {active, lost, written_off}. Фізична доступність обчислюється як state = active і відсутність Loan з порожнім returned_at. Поле available та збережене право на видачу не додаються.
3. Бронюється Book за будь-якої доступності Copy, включно з відсутністю примірників. Кожне повторне бронювання має власний UUID. Reservation.status належить {active, fulfilled, cancelled, expired}; нова Reservation має status = active.
4. Активна черга містить лише active Reservation. Порядок: reserved_at ASC, потім id ASC, де UUID порівнюється лексикографічно в канонічному записі нижнього регістру. За черги право має читач першого бронювання; без черги — будь-який наявний Reader.
5. Одночасно допускається не більше одного відкритого Loan на Copy. due_at >= loaned_at; заповнений returned_at >= loaned_at; рівність допустима. Повернення записує returned_at без автоматичної зміни Copy.state. Зміна state не закриває Loan.
6. C5 координує видачу, а C7/C8 забезпечують її єдину транзакційну межу. Попередні читання через IAvailability/IQueue потрібні для перевірок, але не є остаточним дозволом.
7. Усередині issueCopyAtomically повторно перевіряються актуальний Copy.state, відсутність відкритого Loan та право за поточною головою черги Book. Лише за дозволу створюється Loan з UUID, FK, датами й порожнім returned_at; якщо право визначила перша Reservation, саме вона стає fulfilled. Усі ці зміни фіксуються разом. Інші бронювання, попередня історія й Copy.state незмінні.
8. Конкуренція враховується для спільних даних Copy та черги Book; конкретна ізоляція чи блокування не обираються. Повторна перевірка має бути узгоджена зі змінами, а не окремим незахищеним читанням перед записом. Для двох коректних конкурентних спроб одного доступного Copy без черги рівно одна успішна, інша відхиляється через відкритий Loan за D40.
9. Успіх повертається після commit. Відмова або збій до commit не залишає нового Loan чи часткового fulfilled. Втрата відповіді після commit залишає видачу збереженою; тайм-аут не означає rollback. Ідемпотентність повторного HTTP-запиту та exactly-once не визначені.

Транзакція видачі не охоплює очікування реакції бібліотекаря або виклик A1. A1 не є передумовою UC-10 і не змінює результат уже оформленої видачі.

## 7. Інтеграція A1 та наскрізні NFR

C6 читає фізичну доступність і першу active Reservation, отримує Reader.email цього читача та Book.id/title і передає ці дані A1. Передавання або помилка не змінює Copy, Loan, Reservation чи порядок черги. Помилка показується бібліотекарю з посиланням на відповідну Book. Після повідомлення видача знову перевіряє актуальні дані.

A1 — зовнішній компонент на Component Diagram, що не змінює рішення Lab 2 про відсутність окремого UML-актора сервісу на Use Case Diagram. Механізм виявлення можливості сповіщення, постачальник, API, строк доставки, retry і журнал доставки не визначені. INotifications позначає логічний системний виклик, а не погоджений scheduler, webhook чи публічний endpoint.

## 10. PlantUML та рендер наступних етапів

Плановий комплект: `lab5/components.puml`, `lab5/render/components.svg`, `lab5/render/components.png`; інструкції й інструменти додаються лише на наступних етапах. Джерело — UTF-8, одна UML Component Diagram з українськими назвами та сталими технічними ID C1–C8/A1. Потрібні компонентні символи, provided/required інтерфейси (lollipop/socket або еквівалентна однозначна UML-нотація з легендою) та залежності споживач → постачальник. Декоративні зв'язки без інтерфейсу/пояснення не додаються. Це Component Diagram, а не повтор ER, Sequence чи схема розгортання.

Для інструментарію планується PlantUML 1.2026.9, уже зафіксований у [toolchain Lab 4](../lab4/tools/toolchain.json). Його JAR можна повторно використати без зміни Lab 4; перевірити SHA-256 з цього джерела. Перед рендером зафіксувати фактичні Java, ОС, шрифт і, якщо використовується, Graphviz. Локальний JRE для підготовки матеріалів може працювати у Windows; це не змінює Linux x64 як вимогу до майбутнього сервера.

Обов'язкові кроки: справжній `-checkonly`, генерація SVG і PNG з одного джерела, перевірка відкриття форматів, візуальний огляд, повторна генерація та контроль актуальності. Маніфест майбутнього комплекту має містити версії й SHA-256 джерела, інструментів/конфігурації та зображень. Перевірка актуальності не переписує збережені артефакти; помилка має ненульовий exit code. Побайтовий збіг перевіряється в одному зафіксованому середовищі, не гарантується між різними шрифтами й ОС. Інструменти Lab 4 містять Activity-специфічні перевірки; вони не вважаються готовим валідатором Component Diagram.

## 11. Аудит та Definition of Done

Аудит наступних етапів перевіряє: відповідність spec ↔ діаграма ↔ рендери; повноту компонентів та інтерфейсів; правильність залежностей; збереження доменних правил і транзакційної межі; трасування до попередніх моделей; відсутність зайвих інтеграцій; реальність доказів. Для знайденої розбіжності вказати джерело, наслідок, фактичне виправлення та повторну перевірку. Якщо помилки не знайдені, записати це без вигаданої історії. Відтворення діаграми не є поведінковим, безпековим чи навантажувальним тестом застосунку.

**Definition of Done Етапу 2:**

- Окремий клон має правильний origin; після fetch база дорівнює зазначеному SHA.
- HEAD гілки `feat/lab5-components` походить від цієї бази; створено лише `lab5/spec.md`.
- Spec містить усі розділи, доменні правила, provided/required контракти та перевірювані AC5-01–AC5-15; локальні посилання ведуть до наявних джерел.
- Перевірено зміст і diff, `git diff --check` пройдено; один коміт із заданим повідомленням містить лише spec.
- UML-джерело ще відсутнє; push/PR не виконані; робота зупиняється до підтвердження Етапу 3.

**Definition of Done повної Lab 5, для наступних етапів:**

- AC5-01–AC5-15 виконані з доказами; UML-джерело створене після коміту критеріїв.
- Є діаграма, актуальні SVG/PNG, відтворювані перевірки та інструкція запуску в lab5/.
- Додані README, ADR про модульну архітектуру/атомарність/межу A1, фактичний аудит і DEFENSE; дозволено об'єднати пов'язані рішення в один ADR.
- Візуальний огляд виконано й описано чесно; поведінкові тести відсутнього застосунку мають статус NOT RUN.
- Lab 1–4 і кореневі файли незмінні. Особистий перегляд студентом та фактичне подання викладачеві не позначаються виконаними без підтвердження. Публікація потребує окремої вказівки студента.

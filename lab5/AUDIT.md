## 3. Компоненти, інтерфейси й граф

Відповідальність C1 — український UI; C2 — HTTP, сесії/права/допуск; C3 — Reader; C4 — каталог/Copy; C5 — обіг/бронювання, Availability/Queue; C6 — A1; C7 — Data Access; C8 — спільна БД. Це відповідає architecture §3. Немає окремих мікросервісів для lifeline, додаткових Payment/OAuth або доменної сутності Notification. C6 через IStore лише читає.

| Інтерфейс | Provided | Усі required споживачі |
|---|---|---|
| IBackend | C2 | C1 |
| IReaders | C3 | C2 |
| ICatalogue | C4 | C2 |
| ICirculation | C5 | C2 |
| IAvailability | C5 | C4, C6 |
| IQueue | C5 | C6 |
| INotifications | C6 | C2, системний контекст A1 |
| IStore | C7 | C3, C4, C5, C6 |
| IDatabase | C8 | C7 |
| INotificationGateway | A1 | C6 |

Сума required-споживань — 14. Всі відповідають provider: 1+1+1+1+2+1+1+4+1+1. C6→C5 має два інтерфейси, тому унікальних пар 13. Топологічний порядок C1, C2, C3, C4, C6, C5, C7, C8, A1 доводить ациклічність цього графа. Відповіді у зворотний бік не є новими required-залежностями. Access/Admission усередині C2, Availability/Queue усередині C5; штучних self-споживачів немає.

Provider показаний суцільним приєднанням до іменованого кола, required — UML usage до цього кола; значення пояснено легендою. Це дозволена spec еквівалентна нотація provided/required, а не неозначені звичайні стрілки. Групи Library/Server та примітки не додають компонентів або бізнес-залежностей.

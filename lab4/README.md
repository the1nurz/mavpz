## Рендер і тести

Команди виконуються з кореня репозиторію у Windows x64. Потрібен Node.js у PATH. Повторний аудит перевірено з Node.js 22.23.3, початковий інструментарій також запускався з 24.22.1. Setup завантажує зафіксовані Temurin JRE 21.0.13+9 та PlantUML 1.2026.9 у `.cache/lab4`, перевіряючи SHA-256.

```powershell
powershell -NoProfile -File lab4/tools/setup.ps1
node lab4/tools/validate.mjs --render
node lab4/tools/validate.mjs --check
node lab4/tools/test-validation.mjs
git diff --check
```

`--render` перевіряє справжній синтаксис PlantUML і генерує шість зображень та manifest. `--check` повторює генерацію в пам'яті та порівнює збережені файли побайтово. Регресійні проби працюють в ізольованій копії. За відсутності Java/JAR скрипти повідомляють `NOT RUN` і завершуються кодом 2. Подробиці середовища та перевірок наведено у [validation.md](validation.md).

## Підтверджені результати

Повторний аудит `fa56a2ae6b1e1307be3cd412110a88ba0e024959` зафіксував PASS справжнього парсера, структурного валідатора, семи регресійних мутацій, відкриття й огляду зображень, побайтового повтору та `git diff --check`. Джерело містить 13 пар if/else й один fork/join. Перевірено 14 скінченних серверних шляхів і по два результати інших проєкцій, максимум одну A08 на серверному шляху.

Виправлення AUD-01–AUD-03 внесено у `20be573bd3271460a3e246099f012779c1db5b59`. Початкові spec, Activity, доріжки/події та інструментарій створено відповідно в `cfc83c7`, `cd7d9ef`, `1f5bf16` та `0cbbf32`. Повні SHA й історичні результати містяться в [AUDIT.md](AUDIT.md).

Поведінкові тести застосунку, БД, HTTP та навантаження мають статус **NOT RUN**. Час очікування, транспортна кореляція й повтор запиту після втрати відповіді залишаються питаннями UC-10 X3. Побайтове відтворення залежить від зафіксованого середовища та шрифтів.

## Матеріали для здачі

Комплект етапу 6 складається зі spec, PlantUML-джерела, трьох пар SVG/PNG, manifest, інструментів перевірки, аудиту, ADR та DEFENSE. Для перегляду процесу слід зіставити всі три проєкції з UC-10 і відповідними D33–D41, D48–D55. Для захисту використовується [DEFENSE.md](DEFENSE.md), а результати перевірок підтверджуються командами вище.

Етапи 1–5 мають коміти й перевірений аудит, етап 6 додає пояснення рішення та матеріали захисту. Особистий перегляд студентом і фактична здача викладачеві залишаються непідтвердженими. Етап 7 потребує окремого доручення.

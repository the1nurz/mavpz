## 4. Правила домену, що успадковуються

1. ER незмінна: Publisher, Author, Book, Copy, Reader, Loan, Reservation; 7 сутностей, 30 атрибутів, 7 зв'язків. PK/FK — UUID. Author–Book — прямий M:N без BookAuthor на цьому рівні. Book має рівно одного видавця й щонайменше одного автора; 0 Copy допустимо.
2. Email Reader, ISBN Book та inventory_number Copy — обов'язкові унікальні ключі. Нових правил нормалізації email/ISBN не вводиться. Обов'язковість, FK та кардинальності перевіряються до зміни даних.
3. Copy.state: active, lost, written_off. Доступність істинна лише коли state=active і немає Loan з порожнім returned_at. Доступність і право не записуються окремими атрибутами.
4. Бронюється Book за будь-якої доступності, включно з 0 Copy. Повторна операція створює нову Reservation з новим UUID та власним reserved_at; попередня зберігається. Бібліотекарю право бронювати не додається.
5. Черга: лише status=active; порядок reserved_at за зростанням, потім id лексикографічно в канонічному UUID нижнього регістру. fulfilled/cancelled/expired виключаються. Політик автоматичного скасування/закінчення строку немає.
6. За черги видача дозволена читачеві першої Reservation; без черги — будь-якому наявному Reader. Фізична доступність не означає права обійти чергу. Не більше одного відкритого Loan на Copy, зокрема при конкуренції.
7. Видача атомарно перевіряє актуальність права/доступності та створює новий Loan з порожнім returned_at; коли виконано перше бронювання, саме воно в цій операції стає fulfilled. Решта бронювань, Copy.state й попередня історія незмінні. Попередній read не замінює перевірку в атомарній операції.
8. due_at >= loaned_at, непорожній returned_at >= loaned_at; рівність дозволена. Повернення записує returned_at і перераховує доступність без зміни Copy.state. Зміна state не закриває Loan та не переписує історію.
9. A1 означає передавання email першого читача та Book.id/title зовнішньому сервісу. Передавання/помилка не змінюють доменні записи або чергу. Помилка показується бібліотекарю з Book. Доставка не гарантується; видача перевіряється заново. Подія виявлення можливості сповіщення та її SLA не визначені.
10. Відмова до commit не змінює доменні дані. Збій після commit і втрачена відповідь не доводять rollback. Exactly-once повторного HTTP-запиту не визначено. Пріоритет одночасних причин відмови не встановлюється.

## 6. Повідомлення та return-повідомлення

- Виклик має дієслово, необхідні параметри та визначеного одержувача. Дані відповідають ER; не передавати неіснуючі поля available, role або Notification.id як доменні атрибути.
- Програмні виклики мають формат `operation(parameters) — українське пояснення`. Це назви логічних операцій, а не твердження про реалізовані класи, API чи SQL. Команди людини інтерфейсу та return-повідомлення зберігають зрозумілі формулювання і результати.
- Синхронні виклики показувати суцільною стрілкою `->>`, returns — пунктирною `-->>`. Не нав'язувати асинхронну модель A1: її API не визначено; показати логічне передавання та відому відповідь/помилку без гарантії доставки.
- Односторонній вихід UI до актора без початкового запиту актора показувати `-)`, а не return. У D47 це показ помилки бібліотекарю; справжній return `UI-->>Flow` завершує `showNotificationFailure`. Це не вибір протоколу A1 чи механізму доставки подій.
- Кожний завершений запит читання має явний return: запис, список, [], boolean або відсутність посилання. Кожний завершений запис — результат фіксації або відмова. Після commit повертається успішний результат; Loan.id обов'язковий для UC-10, Reader.id для SC-01. Не приписувати іншим REQ неописаний формат HTTP-відповіді.
- Відмова містить причину/поле з джерела; код 401/403/503 використовувати лише там, де його визначають NFR. Українські повідомлення без SQL/stack trace/секретів.
- D54 навмисно не має доставленого return клієнту: позначити втрату відповіді, завершити серверну активацію після виконання; не малювати вигадане підтвердження користувачу.
- Не показувати гарантоване A1 → Читач «доставлено» як результат SC-25. У SC-27 факт отримання — задана передумова, не обіцянка доставки.
- Взаємодія завершується явною постумовою: що записано або чому дані незмінні. Допускаються нотатки про атомарність та інваріанти без вибору SQL/блокувань.

## 7. Activation bars

| Код | Конкретне правило |
|---|---|
| A | UI активний під час запиту; сервіс від прийняття до відповіді; кожний виклик Store має окрему коротку активацію, закриту після return. Актор не тримає серверну активацію. |
| B | Правило A плюс вкладені активації реально викликаних Access/Availability/Queue. На кожній гілці відмови всі відкриті активації завершуються. У D40 — дві незалежні активації обробників, не одна довга взаємодія для двох запитів. |
| C | NotificationFlow активний від визначеної можливості до результату передавання; Availability/Queue/Store вкладені; A1 активний лише на логічний виклик. UI бібліотекаря активний при показі помилки. Не тримати активацію до майбутнього звернення читача. |
| D | Caller очікує внутрішній результат; Availability/Queue активні лише на обчислення, Store — на читання. Жодної активації людського актора чи запису похідного атрибута. |

## 8. Комбіновані фрагменти

- `alt`: взаємовиключні умови з джерела — результат пошуку, доступність, відмова, відповідь A1, момент збою. В окремій діаграмі сценарію допускається показати тільки відповідний шлях з guard; не дублювати альтернативний сценарій замість його окремого файла.
- `opt`: умовне виконання першої Reservation разом із Loan. Це не окрема транзакція. Не використовувати opt для обов'язкової валідації.
- `loop`: перегляд кожного Copy, перевірка авторів або кандидатів черги. Межі відповідають фактичній колекції; не додавати retry, polling чи кількість повторів, яких немає у вимогах.
- `par`: тільки конкурентні запити SC-22. Один спільний інваріант збереження не більше одного відкритого Loan; переможець не визначений. Не трактувати par як дозвіл неатомарного check-then-write.
- Після точкового перегляду кожна з 59 діаграм має щонайменше один змістовний alt/opt/loop/par. Для успішних сценаріїв D01, D03/D04, D07–D09 та D26–D30 одногілковий alt явно обмежує збереження й успішні відповіді чинними умовами коректності. Не додається нова гілка відмови: вона або описана окремим сценарієм, або лишається наскрізним контрактом REQ-11/12. Посилання на ці умови в guard не змінюють фактичні Gherkin-теги. Доступність Copy та наявність попереднього бронювання не стають умовами відмови у бронюванні. Позначка «—» у решті плану означає відсутність додаткового фрагмента понад уже показану включену поведінку UC-15.
